# CLAUDE.md

Mobile BDD tests: Gherkin `.feature` files run on an Android device through playwright-bdd + mobilewright.

Your job in this repo is narrow: **implement step definitions marked `// TODO`, using the `mobile-mcp` server to inspect the live app.** Do nothing else unless the user explicitly asks.

## Hard rules

1. **Only fill `// TODO` steps.** A TODO step is a step definition whose body contains only a `// TODO` comment. The comment may carry a hint, e.g. `// TODO: tap the gear icon top-right`. Every other step counts as existing and must stay byte-for-byte unchanged: no refactors, renames, reformatting or typo fixes. For example, `I clear input text filed` is what the feature file matches, so leave the typo.
2. **Never read gitignored or generated files** (listed below). That applies to Read/Grep/Glob and also to shell commands (`cat`, `type`, `Get-Content`, `grep`, `find`, `ls -R`). The one exception is `.env`: you may read it, but never edit it.
3. **Never run tests.** Don't run `npm test`, `npm run test:tag`, `npm run bddgen`, `mobilewright test`, `playwright test`, or anything that wraps them. When you finish, give the user the command to run and stop.

[.claude/settings.json](.claude/settings.json) enforces rules 2 and 3 with deny rules for the common cases. A denied call means you hit the rule. Don't look for another way to do the same thing.

## Off-limits paths

| Path | Why |
|---|---|
| `node_modules/` | Third-party code. Use the mobilewright usage notes below and the mobilewright docs instead. |
| `.features-gen/` | Generated by `bddgen` from the `.feature` files |
| `playwright-report/`, `playwright-bdd-report/`, `test-results/` | Test-run output |
| `logs/` | mobile-mcp server log |
| `package-lock.json` | Generated by npm |

This folder is not a git repo, so `git check-ignore` won't work. [.gitignore](.gitignore) is the source of truth: if an entry is added there, treat it as off-limits too. `.env` is the only gitignored file you may read.

`.env` holds the local device config: `DEVICE_ID`, `APP_ID` and `STEP_DELAY_MS`. Read it to find out which device and app to use. Don't edit it, don't copy its values into step code (mobilewright already reads them from the environment), and don't repeat values other than `DEVICE_ID` and `APP_ID` back to the user.

You may read: `.env`, `features/**/*.feature`, `features/steps/**/*.js`, `mobilewright.config.js`, `package.json`, `.mcp.json`, `.gitignore`, `.vscode/settings.json`, `README.md`. Scope searches to `features/` rather than the repo root so generated folders never come up.

## Layout

- `features/*.feature`: scenarios. Don't edit.
- `features/steps/fixtures.js`: exports `Given`/`When`/`Then` built from `mergeTests(bddTest, mobileTest)`, plus an `AfterStep` delay. Don't edit.
- `features/steps/*.steps.js`: step definitions. TODO steps live here.
- `mobilewright.config.js`: Android; `deviceId`/`bundleId` come from `.env`. Timeouts: action 15 s, expect 10 s, test 30 s.

## Workflow

Goal: for each `// TODO` step (ignore TODO comments that aren't inside a step body; if there are none, say so and stop), write an implementation that matches the step text and works on the live app. You decide at runtime which tools and commands to use and in what order.

Constraints to respect along the way:
- Use the scenarios in `features/` that use the step, and the existing steps in the same file, to understand which screen the app is on and to reuse their helpers and style.
- Use the device and app from `.env` (`DEVICE_ID`, `APP_ID`). Don't allocate a remote device unless the user asks, and release it when done. If `DEVICE_ID` is missing and there are several local devices, or `APP_ID` is missing, ask the user.
- Driving the app through MCP to reach a screen is device inspection, not a test run.
- Verify on the device that the action does what the step text says; for `Then` steps, base the assertion on what is actually on screen.
- Prefer the most stable locator available (ids and accessibility labels over visible text, and text over positional or type-based lookups). Don't hard-code coordinates (`screen.tap(x, y)`). If a fragile locator is the only option, add a comment explaining why and flag it to the user.
- Keep the step expression string exactly as written, because the feature file matches it. You may add `{ screen }` or parameters to that same function's argument list if it needs them.

What you may change:
- Bodies and argument lists of TODO steps.
- New helpers in the same steps file, placed above the TODO step that uses them. Never change existing helpers.
- New imports, but only from packages already in `package.json`. Don't install anything.

Stop and ask instead of guessing when:
- a feature step has no definition at all. Don't create one; ask the user to add a TODO stub.
- a stub has code alongside the TODO.
- the device or app isn't available.
- the element can't be found.
- the step's intent is ambiguous.

## mobilewright usage

`screen` is the fixture. A minimal example:

```js
import { expect } from '@mobilewright/test';
import { When, Then } from './fixtures.js';

When('I tap {string}', async ({ screen }, label) => {
  await screen.getByText(label, { exact: true }).tap();
});

```

For anything beyond this example, rely on the mobilewright documentation ([npm page](https://www.npmjs.com/package/mobilewright)) and on how existing steps in `features/steps/` do it, not on `node_modules/`.

Don't add sleeps or `setTimeout`: actions and `expect()` already wait, and `STEP_DELAY_MS` exists for slowing runs down. Assert with `expect(...)`, not `isVisible()`.

## Finishing

End with a short report:
- Each step you filled: its text, `file:line`, and a one-line reason for the locator you chose.
- Each TODO you left unfilled, and what you need to finish it.
- The command for the user to run:

  ```
  npm test                                         # all scenarios
  npm run test:tag -- "<scenario name or @tag>"    # one scenario
  npm run report                                   # open the HTML report
  ```

Don't run these yourself, and don't say the steps pass, because you haven't run them.
